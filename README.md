## 本サービスについて

本サービスは、**エンジニアの方が普段の技術学習や開発業務に取り組む際に、チャット形式で気軽にメモをとり、その内容を 今日学んだこと（TIL）として GitHub リポジトリに記録できるタスク管理×作業メモアプリです。**

以下の一連の流れをアプリ内で完結していることが本サービスの特徴です。

### Step 1. タスクページを作る 🗒️

取り組む内容に応じてタスクページを作り、ページで達成する項目を ToDo リストに設定します。

https://github.com/user-attachments/assets/adb68062-fb16-4ef2-92e2-97eb40dd7677

### Step 2. タスクページで気づいたことをメモする 📝

タスクページで作業中に気づいたことや調べたことのメモ、またコードスニペットや参考にした記事の投稿を行うことができます。

https://github.com/user-attachments/assets/bee08207-d372-4956-8875-28e7bd9352dc

### Step 3. メモをもとに 今日学んだこと（TIL）を書き、GitHub リポジトリに記録する 🍀

作業を完了すると、メモを参考に 今日学んだこと（TIL） を書き、GitHub リポジトリに学習成果を記録できます。

https://github.com/user-attachments/assets/388c2e70-9d69-4719-9a1f-eb9d66261c0b

## 本サービスの開発の背景

私は普段の開発や学習を進める際、GitHub Issue でタスク管理を行いながら、作業中の気づきや調べた内容は Notion や Mattermost など複数の別々のツールにメモしていました。
しかし、この方法では「このタスクで何を行い、何に気づいたか」が複数のツールに分散されてしまい、後から振り返る際に複数のツールを探し回る必要があり非効率でした。また、作業中に得た知見も整理されないまま埋もれてしまいがちで、せっかくの学びが十分に活かされないという課題がありました。

こうした課題を解決するには、**タスクと作業メモを同じ場所で管理できる仕組みが必要**だと考えました。

加えて、エンジニアの間で広まっている TIL（Today I Learned）文化にも共感しており、日々の作業メモをそのまま学習記録として残せれば、メモをとるモチベーション自体も上がると気づきました。つまり、**メモをとることと TIL を書くことには強い親和性がある**と考えたのです。

そこで、GitHub Issue のタスク管理 UI と Claude のチャット形式の UI を参考にしながら、**タスク管理・作業メモ・学習記録の 3 つの機能を一つに統合したアプリ「めもTIL」** を開発しました。

## 主な機能

### A. タスクページ内の操作

1. [タスクページの作成・編集・削除](#a-1)
2. [タスクページ内の ToDo の作成・編集](#a-2)
3. [タスクページ内のメモの投稿・削除](#a-3)
4. [タスクページのステータス変更](#a-4)

### B. GitHub アカウントとの連携によるリポジトリ, md ファイル作成

1. [GitHub 認証, 連携](#b-1)
2. [タスクページ内の GitHub 上のリポジトリ, md ファイル作成](#b-2)

<a id="a-1"></a>

### A.1. タスクページの作成・編集・削除

- タスクページ作成・編集時に、タイトル・概要の入力とタグの設定ができます。
- タグはオートコンプリートで候補を表示し、既存タグの追加や新規のタグ名の入力ができます（1 タスクあたり最大 5 件まで）。
- 「タスクを削除する」ボタンをクリックすると、タスクページを削除できます。

<a id="a-2"></a>

### A.2. タスクページ内の ToDo の作成・表示・編集・削除

- ToDo フォームの「追加」ボタンをクリックすると、ToDo フィールドを追加できます。
- ToDo フィールドは最大 5 個まで追加可能です。
- 各 ToDo フィールドの「×」ボタンをクリックすると、ToDo フィールドを削除できます。
- ToDo リストの「✒️」ボタンをクリックすると、ToDo フォームに切り替わります。

<a id="a-3"></a>

### A.3. タスクページ内のメモの投稿・表示・削除

- 「メモ」タブから"テキストメモ"と"コードスニペット"の投稿を行えます。
- 「参照 URL」タブから参照した"ドキュメント"の投稿を行えます。
- "コードスニペット"はシンタックスハイライト表示されます。
- "ドキュメント"は OGP カード形式で表示されます。
- 各ポストの下部にある「🪣」ボタンをクリックすると、ポストを削除できます。

<a id="a-4"></a>

### A.4. タスクページのステータス変更

- タスクには「Doing」と「Done」のステータスがあり、ボタンをクリックすると切り替わります。

<a id="b-1"></a>

### B.1. GitHub 認証, 連携

- ログイン画面から GitHub アカウントによる認証が可能です。
- また、メールアドレスでログインしている方は、ステータスが「Done」の状態のタスクページの右サイドバーから GitHub アカウントとの連携が可能です。

<a id="b-2"></a>

### B.2. タスクページ内の GitHub 上のリポジトリ, md ファイル作成

- GitHub アカウントと連携しているユーザーは、ステータスが「Done」の状態のタスクページの右サイドバーから、 GitHub 上のリポジトリを作成できます。
- また、GitHub 上のリポジトリを選択し、リポジトリ下に md ファイルの作成もできます。

<a id="c-1"></a>

### C.1. 確認メールによる認証

- サインアップ後、登録したメールアドレス宛に確認メールが送信されます。
- 確認メール内のリンクをクリックすると確認が完了し、そのメールアドレスでログインできます。
- 未確認のメールアドレスでログインしようとすると、アラートメッセージが表示され、確認メールの再送信画面へのリンクが表示されます。

<a id="c-2"></a>

### C.2. リクエストメールによるパスワードリセット

- ログイン画面からパスワードリセットリクエスト画面へアクセスできます。
- 登録済み、かつ、確認済みのメールアドレス宛にリクエストメールを送信できます。
- リクエストメール内のリンクをクリックするとパスワードリセット画面へアクセスし、パスワードの変更ができます。

<a id="c-3"></a>

### C.3. ゲストユーザーの自動生成

- ログイン画面からゲストユーザーを自動生成し、そのアカウントでログインできます。
- ゲストユーザーが利用可能な機能は制限し、ゲストユーザーが GitHub 連携、および、GitHub 上のリポジトリ, md ファイルの作成を行うことはできません。

<a id="c-4"></a>

### C.4. ユーザーの編集・削除

- ヘッダー右のアイコンからアカウント設定画面へアクセスできます。
- ユーザー名とメールアドレスの変更ができます。（メールアドレスの変更方法は後述します）
- 「アカウントを削除」ボタンをクリックすると、ユーザーを削除できます。

<a id="c-5"></a>

### C.5. 確認メールによるメールアドレスの変更

- アカウント設定画面から新しいメールアドレスを入力すると、そのメールアドレス宛に確認メールが送信されます。
- 確認メール内のリンクをクリックすると確認が完了し、メールアドレスが変更されます。

<a id="d-1"></a>

### D.1. タスクページのキーワード検索（オートコンプリート）

- タスクページの「タイトル」に対して、キーワード検索できます。オートコンプリート機能により、文字を入力するとリアルタイムで検索結果を表示します。

<a id="d-2"></a>

### D.2. タスクページのフィルタリング

- タスクページの「ステータス」でフィルタリングできます。

<a id="d-3"></a>

### D.3. タスクページのページネーション

- ページネーションにより、1 ページあたり 24 件まで表示する。

## 使用技術と選定理由

| :--------------------- | :------------------------------ |
| フロントエンド         | Hotwire (Turbo / Stimulus)      |
| スタイリング           | Tailwind CSS / daisyUI          |
| バックエンド           | Ruby 3.3 / Rails 7.2            |
| データベース           | PostgreSQL                      |
| 認証/認可              | Devise, GitHub OAuth (OmniAuth) |
| 検索・ページネーション | Ransack, Kaminari               |

| CI/CD                  | GitHub Actions                  |
| インフラ               | Render                          |

### バックエンド

バックエンドには Ruby on Rails を採用しました。

本アプリでは、タスク、メモ、ToDo、タグ、TIL作成、GitHub連携など、複数の機能を一つの流れとして扱う必要がありました。Rails は MVC、Active Record、ルーティング、バリデーションなど、Webアプリケーションの構造を整理する仕組みが標準で整っており、複数のモデル同士の関連や業務ロジックを、規約に沿って一貫性のある形で実装しやすい点が本アプリに適していると判断しました。

また、認証やOAuth連携のように安全性や信頼性が求められる領域では、Devise や OmniAuth など実績のあるGemを活用しました。こうした基盤部分に信頼性の高いライブラリを取り入れることで、実装コストを抑えつつ、アプリケーションの安定性を高められると考えました。

そのうえで、開発リソースを本アプリ独自の価値である「タスクページ内にナレッジを蓄積し、TILとしてGitHubにアウトプットする」という業務フローや体験設計に集中できる点も、Railsを採用した理由の一つです。

### フロントエンド

フロントエンドには Hotwire（Turbo / Stimulus）を採用しました。

React や Next.js などを用いてフロントエンドを独立したアプリケーションとして構築する構成も検討しましたが、本アプリでは、複雑な状態管理を伴うリッチなUIよりも、画面遷移や一部の操作を滑らかにすることを重視しました。

具体的には、Turbo によるポスト投稿後の一覧更新や画面遷移の高速化、Stimulus による ToDo フォームの追加・削除、検索時のオートコンプリートなど、ユーザーが頻繁に操作する部分の使いやすさを高めたいと考えていました。

Hotwire は Rails との親和性が高く、サーバーサイドレンダリングを中心にしながら、Turbo による画面遷移や部分更新、Stimulus による必要最小限の JavaScript 実装を行えます。そのため、フロントエンドとバックエンドを大きく分離する構成よりも、学習コストや実装コストを抑えつつ、本アプリに必要なユーザー体験を実現しやすいと判断しました。

### インフラ

インフラには Render を採用しました。

Fly.io や Heroku も検討しましたが、個人開発として継続的に運用することを考えた際に、料金体系の分かりやすさと運用コストの見通しやすさを重視しました。

本アプリは、ポートフォリオとして公開するだけでなく、今後も継続的に改善しながら運用していくことを想定しています。そのため、従量課金によって想定外の費用が発生しやすいサービスよりも、コストを管理しやすい Render が適していると判断しました。

また、Render は Rails アプリケーションのデプロイ事例が多く、PostgreSQL、環境変数の管理、GitHub連携による自動デプロイにも対応しているため、本アプリの構成と相性が良いと考えました。

## 本アプリの開発で工夫した点

### 3つの認証方法を両立する設計

本アプリでは、**メールアドレスとパスワードによる認証**、**GitHub OAuth認証**、**ゲストログイン**の3つの認証方法を実装しました。

認証機能の基盤には Devise と OmniAuth を使用していますが、単にGemを導入するだけではなく、本アプリの利用シーンに合わせて認証フローをカスタマイズしています。

**メールアドレスで登録**するユーザーには、**サインアップ時の確認メール**、**パスワードリセット**、**メールアドレス変更時の再確認メール**を用意しました。これにより、継続的にアプリを利用するユーザーが、安全にアカウントを管理できるようにしています。また、未確認ユーザーがパスワードリセットを行えないように制御し、メール認証が完了していない状態でアカウント操作が進まないようにしました。

**GitHub OAuth認証**では、認証成功時にGitHubのユーザー識別ID、名前、メールアドレス、アクセストークンを取得し、アカウントを作成しています。本アプリでは、このアクセストークンによりGitHub APIを利用し、GitHubリポジトリやMarkdownファイルを作成する機能があります。GitHub OAuth認証でログインしたユーザーは、初回ログイン時点でアクセストークンを取得できるため、追加の連携操作なしで当該機能をスムーズに行えます。

**ゲストログイン**は、アプリを試したいユーザー向けに実装しました。通常のメールアドレス認証やGitHub OAuth認証では、Devise/Wardenが認証後のセッション管理を行います。一方でゲストログインは、パスワードやOAuthによる認証情報を持たないため、Deviseの標準的な認証フローだけではログイン状態を管理できません。**そこで、一時的なUserレコードを作成し、そのIDをsessionに保持したうえで、独自のWarden strategyから該当ユーザーを取得して認証済みユーザーとして扱う実装にしました。**

また、ユーザー種別に応じた細かな制御も行っています。ゲストユーザーはアカウント設定画面へアクセスできないようにし、GitHub OAuth認証ユーザーとゲストユーザーはメール確認フローをスキップするなど、認証方法ごとの利用形態に合わせて処理を切り替えています。

さらに、**メールアドレスで登録したユーザーやゲストユーザーは"完了した"タスクページ内からGitHub連携できるように導線を用意しています。**OAuth認証成功後、既存のUserレコードにGitHubの識別IDとアクセストークンを追加する設計にしています。これにより、ユーザーはアカウントを作り直すことなく、必要になったタイミングでGitHubリポジトリやMarkdownファイル作成機能を利用できます。さらに、同じGitHubアカウントがすでに別ユーザーに連携されている場合は例外処理を施し、アカウントの重複連携を防ぐようにしています。

このように、**DeviseやOmniAuthという信頼性の高いgemを使用し認証の安全性を確保しつつ、ユーザーの利用目的に応じて認証方法を選べる設計**と、**認証方法ごとの権限・確認フロー・GitHub連携可否を制御する独自実装を行ったこと**が工夫した点です。
